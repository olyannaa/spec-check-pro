# Зафиксированное решение

Сводка кейса, кастдева и файлов кейсодателя. Архитектура от этого дампа **не меняется**.

## Продукт

Внутренний веб-инструмент предварительного ревью ТЗ NET (потоки и витрины радиосети).

Пользователь — аналитик (в команде ~14 человек). Соседние команды документ читают как потребители данных, но кнопку «Проверить» жмёт автор ТЗ.

Сейчас: Confluence + устные правки на дейликах. Встроенная LLM в Confluence даёт нерелевантные ответы и плохо держит контекст. ТЗ пишут минимум раз в неделю. ПД в документах нет.

Целевой процесс: аналитик дописал ТЗ → прогон через нас → принимает или отклоняет замечания → дорабатывает сам → отдаёт в разработку.

ИИ не ставит «готово к разработке» и **не исправляет текст**.

## Что сдаём на демо

Не своя модель, не MCP, не skill, не чат.

Веб-страница: PDF или текст → выбор LLM (Qwen / Kimi / внутренняя) → 10–20 комментариев к местам:

- фрагмент / раздел;
- почему это стоп для разработки или теста;
- какой вопрос закрыть в ТЗ;
- тяжесть blocker / should_fix / nit;
- чей взгляд: аналитик по шаблону / разработчик / тестировщик;
- общий вердикт по документу.

## Архитектура (коротко)

```
PDF/текст → ingest (историю страницы выкинуть)
         → parse по шаблону (текст + таблицы)
         → 8 обязательных правил + покрытие разделов
         → LLM, три роли одной модели
         → merge (пропуск хуже придирки)
         → комментарии в UI
```

Знания в репозитории, не RAG по Confluence. Связанные документы не подтягиваем. Внутренний контур в проде; на хакатоне любая совместимая LLM.

Подробности: [PLAN.md](../PLAN.md).

## Жёсткие ограничения

| Можно | Нельзя |
| --- | --- |
| Проверка **после** написания | Помощник в момент письма |
| Указать место и вопрос | Переписать абзац / сгенерировать ТЗ |
| 10–20 замечаний, спорные оставлять | Резать находки ради «чистоты» |
| PDF и текст (плюс простые форматы, если успеем) | Confluence, MCP, внешние плагины |
| Выбор LLM в UI | Fine-tune |
| Разделы шаблона, в т.ч. авторские блоки если всплывут | Ревью «Истории изменений» |

Оффтоп «собрать ТЗ формой по шаблону» — не хакатон.

## На чём учим проверку

Уже есть:

- один шаблон «Потоковые данные/витрины» — [TEMPLATE.md](TEMPLATE.md)
- 8 обязательных правил — [CHECKLIST.md](CHECKLIST.md)
- 3 примера (поток, источник, витрина) — `samples/`
- эталон дыр в них — [SAMPLE-FINDINGS.md](SAMPLE-FINDINGS.md)

Фокус поверх шаблона: Kafka-кластеры и пути, поля и логика расчёта, фильтры, обновление и объём.

Официальный тест — **новый** документ витрины-агрегата, не эти три файла.

Ждём: файл точечных дорогих ошибок; комментарии к примерам, если пришлют. Шаблон могут чуть поменять, каркас стабилен. Если витрины вынесут в отдельный шаблон — чеклист тем же файлом, конвейер не трогаем.

## Критерий успеха

Кейсодатель смотрит полезность на живом ТЗ:

- находка про этот документ, не «уточните требования»;
- видно, какой фрагмент;
- формулировка понятна аналитику;
- по вердикту можно решить, отдавать ли в разработку.

Для себя: не потерять ни один пункт из 8 правил и эталона. Лишняя придирка с цитатой допустима.

## Ещё открыто — не блокирует сборку

- Файл с дорогими неочевидными ошибками
- Разведут ли шаблон потока и витрины на два файла
- Авторские блоки вне шаблона: если появятся — ревьюим, не игнорируем
- Показывать ли confidence модели: нет, только severity
