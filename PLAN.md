# Стартовый план: ИИ-ревью технических заданий NET

Команда: **1 продакт + 2 AI-инженера**.  
Кейс: предварительное ревью ТЗ на новые потоки и витрины данных. ИИ не заменяет аналитика и не ставит «можно в разработку».

## Зачем это бизнесу

Сейчас ТЗ вычитывают вручную. Часть неоднозначностей всплывает уже в разработке или на тестах: документ возвращается аналитику, команда заново согласовывает требования, чинит реализацию и перетестирует.

Решение считается успешным, если на реальном ТЗ оно:

- находит места, которые **действительно** стоит уточнить;
- привязывает замечание к **конкретному фрагменту** документа;
- объясняет **почему** это будет непонятно разработчику;
- говорит **что дописать**;
- не сыплет общими советами «уточните требования».

---

## MVP на демонстрацию

Один сценарий, без Confluence и без авторизации.

1. Аналитик вставляет текст ТЗ (или выбирает пример).
2. Агент анализирует документ.
3. На экране:
   - общий вердикт (`можно передавать` / `нужна доработка` / `не готово`);
   - список замечаний;
   - цитата из ТЗ;
   - раздел документа;
   - почему это риск для разработки;
   - что уточнить.
4. Аналитик решает, что править. ИИ не принимает итоговое решение.

Вне скоупа хакатона: Confluence, Jira, согласования, генерация ТЗ, автоисправление текста.

---

## Что сдаём: не модель, а агент ревьюера

Авторы кейса написали «LLM-модель или ИИ-агент», потому что им всё равно, fine-tune это или промпт. Им нужен инструмент: на вход текст ТЗ, на выход предварительное ревью. Обучать свою модель не будем — нет размеченного корпуса, нечем мерить, не успеем.

**Итог хакатона — узкий агент ревьюера**, а не чат и не «своя LLM».

Аналитик не переписывается с моделью. Он нажимает «Проверить» и получает артефакт проверки: вердикт + список находок по контракту ниже. LLM внутри — судья по неоднозначным формулировкам, не продукт.

Как это устроено:

1. Парсер режет ТЗ на разделы, таблицы, цитаты.
2. Чеклист сверяет покрытие с шаблоном.
3. Эвристики ловят дыры, которые правилами видно сразу (пустой раздел, «и т.д.», нет типа в маппинге).
4. LLM смотрит документ **глазами разработчика NET**: противоречия, неявное зерно, двусмысленные правила.
5. Склейка выкидывает дубли и общие советы без цитаты.

Это агент в рабочем смысле: цель, фиксированные шаги, инструменты (парсер, чеклист), LLM для суждения. Это не рой из десяти агентов и не дообучение. На демо продакт показывает экран аналитика, инженеры за 2 минуты показывают конвейер и промпт.

Почему не голый ChatGPT: без шаблона, без таксономии правок и без требования цитаты модель скатывается в «уточните требования». Именно это кейсодатель просит не делать.

## Контракт выхода (зафиксировать в день 1)

Каждое замечание — один объект:

| Поле | Зачем |
| --- | --- |
| `severity` | `blocker` / `should_fix` / `nit` |
| `section` | раздел ТЗ, не «документ целиком» |
| `quote` | точная цитата или пометка «раздел отсутствует» |
| `why` | почему разработчик остановится |
| `ask` | конкретный вопрос аналитику |
| `category` | тип проблемы из таксономии ниже |

Общий результат:

- `verdict`
- `summary` на 3–6 предложений: что мешает передаче в разработку
- `findings[]`
- `covered_sections` / `missing_sections` относительно шаблона

Правило качества: если замечание можно вставить в любое другое ТЗ без правки — оно плохое. Выбрасываем.

## Таксономия замечаний

Берём не «стиль текста», а то, на чём обычно спотыкается разработка потоков и витрин:

1. **Зерно и ключи** — что является строкой витрины, чем уникальность, как дедуп.
2. **Источники** — система, объект, фильтр выборки, свежесть, владельцы.
3. **Маппинг полей** — тип, null, единица измерения, пример, источник поля.
4. **Джойны и приоритет источников** — тип джойна, что делать при нескольких совпадениях.
5. **Инкремент и история** — full/incremental, окно пересчёта, late data, SCD / «актуальная запись».
6. **Время** — таймзона, граница суток, event time vs load time.
7. **Качество** — допустимые дыры, отказ пайплайна vs quarantine, сверка с источником.
8. **Расписание и SLA** — когда готово, что если источник опоздал.
9. **Объём и хранение** — оценка объёма, глубина истории, партиции.
10. **Неоднозначный язык** — «как правило», «при необходимости», «и т.д.», «по аналогии с …».
11. **Пустые обязательные разделы шаблона**.
12. **Противоречия между разделами** — зерно в одном месте, другое в маппинге.

Продакт на демо показывает 5–8 сильных замечаний, а не 40 слабых.

## Что уже известно без файлов от кейсодателя

Примеры ТЗ обещаны ближе к старту. Нельзя ждать их, чтобы начать думать.

До получения данных восстанавливаем **рабочую гипотезу шаблона** для ТЗ NET (потоки/витрины радиосети, текст нейтрализован):

1. Паспорт документа (название, версия, автор, дата, тип: поток / витрина).
2. Цель и потребитель результата.
3. Источники данных.
4. Целевой объект (схема, таблица/топик, зерно).
5. Ключи, дедупликация, историчность.
6. Маппинг полей и преобразования.
7. Бизнес-правила и исключения.
8. Инкрементальность, расписание, опоздания.
9. Правила качества и реакции на брак.
10. Объёмы, SLA, зависимости.
11. Критерии приёмки.
12. Открытые вопросы.

Это гипотеза. Как только придут шаблон и примеры — сверяем 1-в-1 и правим чеклист, а не архитектуру агента.

Типичные правки разработки (гипотеза, потом сверить с реальными корректировками):

- не сказано, inner или left;
- «актуальная запись» без правила;
- «ежедневно» без времени и таймзоны;
- «поля как в источнике» без списка;
- ключ есть, дедуп нет;
- фильтр «только активные» без определения активности;
- единицы и точность чисел не заданы;
- несколько источников без приоритета.

## Роли

### Продакт

- Сценарий демо и экран аналитика.
- Определение «хорошего замечания» vs шума.
- Синтетические ТЗ для разработки, пока нет боевых примеров.
- Канал с кейсодателем (@andrewgrhv): шаблон, 2–3 ТЗ, примеры правок разработки.
- Не расползаться в платформу: один поток «вставил текст → получил ревью».

### AI-инженер 1 — понимание документа

- Разбор ТЗ на разделы, таблицы, цитаты.
- Чеклист покрытия шаблона.
- Детерминированные эвристики (пустые разделы, размытые формулировки, дыры в маппинге).
- Привязка finding → quote → section.
- Набор фикстур: «сырое ТЗ», «почти готовое», «после правок разработки».

### AI-инженер 2 — агент и качество находок

- Промпт/агент с ролью разработчика NET.
- Структурированный JSON-выход по контракту выше.
- Слияние эвристик и LLM, дедуп, ранжирование.
- Прогон на фикстурах: полезно / шум / промах.
- Подключение модели: OpenAI-compatible API + режим без ключа, чтобы стенд не умирал.

Вместе на демо: продакт ведёт сценарий, AI2 показывает как устроен агент, AI1 — почему замечание попало в конкретный абзац.

## Архитектура, которую не придётся выкидывать

```
ТЗ (текст / markdown)
        │
        ▼
   Parser секций
        │
        ├─► Checklist шаблона
        ├─► Heuristics (всегда работают)
        └─► LLM-агент «глазами разработчика» (если есть ключ)
                    │
                    ▼
              Merge + rank
                    │
                    ▼
     Вердикт + список замечаний для аналитика
```

Два слоя специально:

- **Эвристики** — демо живое даже без LLM, находки привязаны к тексту.
- **LLM** — формулирует «почему» и «что спросить», ловит противоречия, которые правилами не взять.

Стек интерфейса: Next.js + TypeScript, один экран ревью. Интеграций нет. Модель снаружи, промпт и таксономия — в репозитории.

## Этапы кейса → конкретные задачи

Совпадает с постановкой хакатона, но в порядке, в котором команда реально стартует.

### 0. До получения данных (сразу)

- Зафиксировать контракт выхода и таксономию.
- Собрать гипотезу шаблона и каталог типовых правок разработки.
- Написать 2 синтетических ТЗ в нейтральном стиле кейса (поток + витрина), с заранее известными дырами.
- Собрать каркас: вставка текста → разбор → список замечаний.
- Написать 10 «золотых» ожидаемых находок по синтетике.

### 1. Анализ шаблона (когда файл появится)

- Разложить разделы: обязательные / желательные / редко заполняемые аналитиком.
- Отметить, что аналитик заполняет до передачи в разработку, а что часто остаётся пустым.
- Обновить чеклист. Не тащить в ревью разделы, которые шаблон не предполагает.

### 2. Анализ примеров ТЗ

- Сопоставить структуру с шаблоном: что реально пишут, что пропускают, как выглядят таблицы маппинга.
- Выписать якоря: как называют зерно, инкремент, источники, DQ.
- Добавить 1–2 реальных (нейтрализованных) ТЗ в фикстуры.

### 3. Анализ корректировок разработки

- Классифицировать правки по таксономии.
- Для каждого класса: триггер в тексте, вопрос аналитику, пример хорошего finding.
- Это главный источник промпта. Не выдумывать стиль замечаний — брать с реальных правок.

### 4. Сборка агента

- Парсер + чеклист + эвристики + LLM.
- Промпт: роль разработчика потока/витрины, шаблон, примеры плохих формулировок, запрет общих советов.
- Постобработка: отрезать находки без цитаты, без `ask`, дубли.

### 5. Тестирование

На каждом ТЗ смотрим глазами аналитика:

| Вопрос | Да / нет |
| --- | --- |
| Находка про это конкретное ТЗ, а не про «документацию вообще»? | |
| Понятно, какой абзац править? | |
| Разработчик реально задал бы этот вопрос? | |
| Вердикт помогает решить, отдавать ли в разработку? | |

Цель на демо: 70%+ показанных замечаний продакт готов защитить перед кейсодателем. Лучше 6 точных, чем 25 размытых.

## План первых шагов (порядок, не календарь)

**Шаг A — синхрон на 30 минут (все трое)**  
Согласовать MVP, контракт JSON, таксономию, что *не* делаем.

**Шаг B — продакт**  
Набросать текст демо. Написать ТЗ-фикстуру «плохую» и «почти хорошую». Сформулировать 5 эталонных замечаний вручную.

**Шаг C — AI1**  
Парсер заголовков/таблиц. Чеклист гипотезы шаблона. Эвристики по размытому языку и дырам маппинга. Подсветка цитаты.

**Шаг D — AI2**  
Схема ответа модели. Промпт разработчика. Склейка слоёв. Заглушка без API-ключа.

**Шаг E — вместе**  
Прогнать обе фикстуры. Выкинуть шум. Зафиксировать «это уже можно показывать».

**Шаг F — когда придут данные кейсодателя**  
Не переписывать продукт. Обновить шаблон, фикстуры, каталог правок, промпт. Повторить прогон.

**Шаг G — демо**  
Одно ТЗ → разбор вслух: вердикт, 3 сильных находки, 1 место где аналитик может не согласиться (показать, что ИИ — помощник, не судья).

## Что запросить у кейсодателя в первый контакт

Коротко, без Confluence:

1. Актуальный шаблон ТЗ (хотя бы оглавление разделов).
2. Два ТЗ: одно «ушло в разработку без боли», одно «вернули на уточнение».
3. 5–10 конкретных правок разработки: было → стало / какой вопрос задали.
4. Что аналитик *обязан* заполнить до передачи задачи, а что можно добить позже.

Пока этого нет — работаем на гипотезе и синтетике, но помечаем в коде `hypothesis`, чтобы не зацементировать выдумку.

## Риски

| Риск | Что делаем |
| --- | --- |
| Примеры ТЗ придут поздно | Синтетика + контракт выхода. Данные подменяют фикстуры, не архитектуру |
| Модель даёт общие советы | Жёсткий контракт, отсев без цитаты, мало замечаний высокого веса |
| Шаблон не совпадёт с гипотезой | Чеклист одним файлом, правится за один проход |
| Команда расползается в «платформу» | Один экран, один API `POST /api/review` |
| Нет ключа LLM на демо | Эвристический слой обязан давать полезный разбор сам |

## Критерий «можно показывать кейсодателю»

- На плохом синтетическом ТЗ агент бьёт в заранее заложенные дыры (зерно, джойн, инкремент, размытый язык).
- На почти готовом ТЗ не устраивает пустой шум.
- Каждое замечание кликается в фрагмент.
- Продакт может за 3 минуты пройти сценарий без объяснения архитектуры.

Дальше — только подмена гипотезы на реальные шаблон, примеры и правки разработки.
