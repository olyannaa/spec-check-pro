# Стартовый план: ИИ-ревью технических заданий NET

Команда: **1 продакт + 2 AI-инженера**.  
Кейс: предварительное ревью ТЗ на новые потоки и витрины данных. ИИ не заменяет аналитика, **не исправляет текст**, только указывает места.

## Вводные от кейсодателя

Сейчас ревью живёт в Confluence: устно или комментариями к странице. Команда NET — 14 человек. Проблема встречается часто, трудозатраты на возвраты ТЗ считают плохо, но времени уходит много.

| Вопрос | Ответ |
| --- | --- |
| Когда проверять | **После** написания ТЗ, не в момент письма |
| Что делать с текстом | Только указать место. **Не исправлять** |
| MCP / Confluence | **Не берём** |
| Модель | Внутренняя LLM. На тестовом кейсе можно любую: **Qwen, Kimi** |
| Поля истории изменений документа | **Невалидны** для нашей задачи, не ревьюим |
| Тестирование | Те же шаблоны, что в ТЗ: прогнать через решение |
| Ложные срабатывания | Хуже пропустить. **Лучше 10 раз придраться, чем пропустить ошибку** |
| Материалы | Предоставят **шаблон** и **комментарии** (как сейчас пишут в Confluence) |

Это не помощник в редакторе и не автоисправление. Это прогон готового документа, результат похож на пачку комментариев к фрагментам.

---

## Что сдаём

**Агент ревьюера с несколькими ролями внутри одной LLM.** Не своя обученная модель, не MCP, не чат, не рой сервисов.

Снаружи — агент: взял готовое ТЗ, прогнал фиксированные шаги, вернул комментарии к местам.  
Внутри — одна модель (Qwen / Kimi / совместимый API) с несколькими ролями, как у тех, кто сейчас комментирует в Confluence:

1. **Разработчик потока/витрины** — зерно, джойны, инкремент, типы, дедуп.
2. **Тестировщик** — приёмка, краевые случаи, DQ, «как проверить».
3. **Читатель шаблона** — какие обязательные разделы пустые или заполнены отпиской. Без полей истории документа.

Один прогон, один экран, один API. Роли — секции промпта или короткие последовательные вызовы той же модели, не отдельные продукты.

Почему так, а не «просто LLM» и не «просто агент»:

- Голый чат без шаблона и комментариев даёт общие советы.
- Агент без ролей смотрит одной линзой и при установке «не пропустить» всё равно слеп к тест-кейсам и пустым разделам.
- MCP и коннекторы к Confluence кейсодатель просил не брать.

---

## MVP на демонстрацию

Аналитик закончил черновик ТЗ → вставил текст → получил комментарии к местам.

На экране:

- список находок, привязанных к фрагменту / разделу;
- почему это может остановить разработку или тест;
- какой вопрос стоит закрыть в ТЗ;
- тяжесть: `blocker` / `should_fix` / `nit` (чтобы 10 придирок не смешивались с дырой в ключе);
- краткий вердикт: сколько блокеров, можно ли отдавать как есть.

Не делаем: переписывание абзаца, «исправленную версию ТЗ», подсказки во время письма, интеграцию с Confluence, MCP, правки полей истории документа.

## Контракт выхода

Комментарий, не патч.

| Поле | Зачем |
| --- | --- |
| `severity` | `blocker` / `should_fix` / `nit` — полнота высокая, сортировка обязательна |
| `role` | чья линза: разработчик / тестировщик / шаблон |
| `section` | раздел ТЗ |
| `quote` | точная цитата или `раздел отсутствует` |
| `why` | почему это место опасное |
| `ask` | вопрос, на который в ТЗ нет ответа |
| `category` | тип из таксономии |

Общий результат: `verdict`, `summary`, `findings[]`, покрытие шаблона без исторических полей.

Правила:

- Каждая находка указывает **место**. Без места — не показываем, кроме отсутствующего раздела.
- Текст ТЗ **не предлагаем заменить**.
- Спорное замечание **не выкидываем**: помечаем `nit` или «спорно», но оставляем. Пропуск хуже лишнего.
- Дубли склеиваем. Пустые «уточните требования» без якоря в тексте — единственный тип, который режем.
- Поля вроде «история изменений», «версия страницы», «кто правил документ» — игнор.

## Таксономия замечаний

Не стиль текста, а то, из‑за чего ТЗ возвращают из разработки (потом сверим с реальными комментариями):

1. Зерно и ключи
2. Источники и фильтр выборки
3. Маппинг полей (тип, null, единица, пример)
4. Джойны и приоритет источников
5. Инкремент и «актуальная запись»
6. Время и таймзона
7. Качество данных и реакция на брак
8. Расписание и SLA
9. Объёмы, глубина, партиции
10. Размытый язык («как правило», «и т.д.», «при необходимости»)
11. Пустые обязательные разделы шаблона
12. Противоречия между разделами

Не входит: оформление Confluence, история правок документа, орфография, «переформулируйте красивее».

## Архитектура

```
Готовое ТЗ
    → Parser секций (историю документа выкидываем)
    → Checklist шаблона
    → Эвристики (дыры без модели)
    → LLM, роль «разработчик»
    → LLM, роль «тестировщик»
    → LLM, роль «шаблон»
    → Merge: дедуп, сортировка по severity, спорное оставляем
    → Комментарии к местам + вердикт
```

Модель: OpenAI-compatible (Qwen / Kimi / внутренняя). Ключ не зашиваем. Без ключа остаются чеклист и эвристики, чтобы стенд не умирал.

Стек: Next.js + TypeScript, один экран «вставил → проверил». Интеграций нет.

---

## Как тестируем

Как сказал кейсодатель: **на таких же шаблонах, прогоном через решение**.

1. Пока нет файлов — 2 синтетических ТЗ в гипотезе шаблона, с заранее заложенными дырами.
2. Когда дадут шаблон и комментарии — кладём 2–3 реальных (нейтрализованных) ТЗ и эталон: какие комментарии люди уже оставляли.
3. Прогон: документ → наш вывод. Смотрим recall по эталону: нашли ли то, что уже ловили разработчики.
4. Ложные срабатывания не штрафуем жёстко. Штрафуем пропуск эталона и находки без места.
5. Отдельно проверяем, что исторические поля шаблона не порождают замечаний.

Метрика для себя: не пропустить ни один эталонный комментарий. Лишние придирки допустимы, если у них есть якорь в тексте.

## Роли в команде хакатона

### Продакт

- Экран «как комментарии в Confluence»: место, текст, тяжесть. Без редактора-соавтора.
- Демо: аналитик закончил ТЗ → прогон → смотрит, что закрыть до разработки.
- Когда придут шаблон и комментарии — разметить эталон для прогона.
- Не тащить MCP, Confluence, автоисправление.

### AI-1 — документ

- Парсер, вырезание невалидных полей истории.
- Чеклист шаблона.
- Эвристики и привязка цитаты.
- Фикстуры и прогон.

### AI-2 — роли в модели

- Три роли в промпте, совместимость с Qwen/Kimi.
- Склейка с уклоном в полноту: спорное не дропать, дубли склеить, без места — выкинуть.
- Режим без ключа.

## Гипотеза шаблона (пока файлов нет)

Рабочая схема ТЗ потока/витрины. После получения шаблона заменить 1-в-1.

1. Паспорт (название, автор, тип: поток / витрина). Поля истории изменений — **не проверяем**.
2. Цель и потребитель.
3. Источники.
4. Целевой объект, зерно.
5. Ключи, дедуп, историчность **данных** (SCD / актуальная запись) — это не история документа.
6. Маппинг и преобразования.
7. Бизнес-правила.
8. Инкремент, расписание, late data.
9. Качество данных.
10. Объёмы, SLA, зависимости.
11. Критерии приёмки.
12. Открытые вопросы.

Типовые комментарии разработки (гипотеза, заменить реальными):

- не сказано inner или left;
- «актуальная запись» без правила;
- «ежедневно» без времени и таймзоны;
- «поля как в источнике» без списка;
- ключ есть, дедуп нет;
- «только активные» без определения;
- несколько источников без приоритета.

## Первые шаги

**A.** Втроём: после написания, только места, recall > precision, без MCP, Qwen/Kimi, историю документа игнор.

**B.** Продакт: экран комментариев, плохое и почти готовое ТЗ.

**C.** AI-1: парсер + чеклист + эвристики.

**D.** AI-2: три роли, JSON, склейка «лучше придраться».

**E.** Прогон фикстур. Смотрим, не потеряли ли заложенные дыры. Лишние nits оставляем, если есть цитата.

**F.** Шаблон и комментарии от кейсодателя → подмена чеклиста, эталона, промпта. Архитектуру не трогаем.

**G.** Демо: одно готовое ТЗ, пачка комментариев к местам, 1 спорное «аналитик может не согласиться», без исправленного текста.

## Риски

| Риск | Что делаем |
| --- | --- |
| Шаблон и комментарии придут позже | Гипотеза помечена, заменяется файлами |
| 10 придирок утопят блокеры | Сортировка по severity, не фильтр |
| Qwen/Kimi раздувают общие советы | Обязателен якорь в тексте |
| Команда полезет в Confluence/MCP | Прямой запрет кейсодателя |
| Ревью истории документа | Чёрный список полей шаблона |
| Нет ключа на демо | Эвристики обязаны найти дыры сами |
